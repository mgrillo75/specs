•	Decoupled lifecycle: the simulator can be killed, restarted, reconfigured, or replaced without touching Ignition at all.
•	Ignition consumes the simulators as plain Modbus TCP devices — exactly the same way it'll consume the real GCSA_RTAC_MODBUS and GCSB_RTAC_MODBUS in production. Only the IP/port changes between sim and prod, which is the cleanest possible FAT story for Robert's team.
•	200 ports on one host is fine for the OS (well under ephemeral port limits and the 65k cap); just make sure 501–700-ish aren't colliding with anything else.
One refinement to your diagram
Don't have Ignition launch and manage the Python process via API call (the arrow in Image 1). Run the simulator as a proper OS service — Windows Service via NSSM, or a systemd unit on Linux — independent of Ignition. Reasons:
•	The Gateway scripting environment isn't a great place to manage a long-lived child process lifecycle. system.util.execute() is fire-and-forget; you'd be reinventing process supervision.
•	Keeping the simulator outside Ignition's process tree means a Gateway restart doesn't kill your sim, and a sim crash doesn't surface as a Gateway issue.
•	It mirrors how the real RTACs will work — they're independent network endpoints Ignition simply connects to.
If you do want runtime control from Ignition (start/stop a specific simulated device, inject a fault, swap CSV scenarios), expose a small REST API on the Python side (Flask/FastAPI, ~20 lines) and call it from Gateway scripting. That's much cleaner than process management.

Short answer: Technically yes, you could launch 200+ instances. Practically, this is a worse choice than the custom Python approach — and it's worse for reasons that matter for your FAT.
Here's why OpenModSim is the wrong shape for what you're trying to do:
It's a Qt desktop GUI application, not a service. Looking at the repo, it's 78.5% C++ with Qt widgets, distributed as omodsim.exe / omodsim.app. There's no headless or service mode in the README — every instance opens a window. That means:
•	200+ desktop windows on one machine. On Windows you're not just dealing with taskbar clutter — you're consuming GDI handles (Windows enforces ~10,000 per session by default), DWM resources, and per-window OS overhead. 200 is in the range where you'll start hitting weird platform limits.
•	It can't run as a Windows Service cleanly. Services run in Session 0 with no interactive desktop; GUI apps need a real session. You'd be stuck running this in a logged-in console session on a dedicated machine, which is fragile and not the sort of thing that survives a reboot or RDP disconnect.
•	Memory footprint is brutal at scale. Each Qt instance pulls in the full Qt runtime, widget tree, event loop, and per-instance state. Realistic per-instance RSS is 60–150 MB. Multiply by 200 → 12–30 GB just for simulator overhead, before any actual register data. Compare to a single async pymodbus process serving 200 ports, which fits comfortably in well under 200 MB total.
Configuration management at 200× is painful. Each OpenModSim instance needs its own config (port, register map, simulation behavior). The tool stores those as .omsm files via its GUI. You'd be either: (a) hand-clicking through the GUI 200 times, or (b) generating 200 config files programmatically and launching the binary with each — at which point you're already writing the kind of orchestration code that makes the GUI tool itself redundant. With pymodbus, your 200 servers live inside one Python process driven by one CSV — the orchestration goes away entirely because there's nothing to orchestrate.
No clean lifecycle control. You mentioned wanting to "Launch, Manage, Close via API" in your earlier diagram. With OpenModSim that means spawning 200 child processes and managing each one's PID, watching for crashes, restarting them individually. With a single pymodbus process, lifecycle is one start/stop. Fault injection (drop a server, change scenario data, simulate disconnects) is one in-process call, not 200 IPC handshakes.
It's optimized for a different job. OpenModSim is genuinely good at what it's built for: an engineer at a workstation interactively poking at a few Modbus servers while debugging a single client connection. It has a slick Qt UI, a log viewer, JavaScript scripting, error injection — all desktop-engineer features. None of those carry over to "run 200 of them on a server in the corner of the rack."
One narrow scenario where it could make sense: if you only need a handful of representative simulators (say, 2–4) and you specifically want the GUI-driven scripting and message inspection during interactive FAT debugging. In that case it's a fine tool — just not for 200.
For your actual use case (200+ ports, headless, CSV-driven, lifecycle-controllable, FAT-grade), pymodbus in a single Python process remains the right answer. ~75 lines of code, one CSV input, one process to supervise, runs as a proper systemd unit or NSSM-wrapped Windows service. Yes — Python with pymodbus is the right call for this specific scenario. I'd commit to it rather than continue language-shopping. Here's the reasoning, including the credible alternatives so you can sanity-check the decision.
Why Python wins for this specific job:
The work is I/O-bound, not CPU-bound. 200 servers responding to periodic Modbus reads is trivial throughput — well inside what a single-core Python asyncio event loop handles with room to spare. The performance gap between Python and a "faster" language is genuinely invisible at this scale and workload, so any argument for a different language has to be made on grounds other than runtime efficiency.
The big find from verifying pymodbus's current state: pymodbus 3.x ships a ModbusSimulatorServer class with a built-in HTTP control surface — endpoints for register handling, call monitoring, response simulation, server start/stop, and JSON-based setup files. You're not writing a Modbus server from scratch. You're configuring one that already exists, with the fault-injection and runtime control hooks already wired up. That alone moves Python from "good choice" to "obvious choice" — every other option means more code to write. PyModbus
A FAT simulator also gets modified mid-test. Operators want to change scenarios, inject faults, swap CSV inputs, simulate disconnects. Iteration speed matters more than runtime efficiency for test infrastructure that isn't the SUT. Python wins that dimension decisively.
Credible alternatives, and why I wouldn't switch:
•	Go (simonvetter/modbus, grid-x/modbus): Genuinely good fit on paper — single static binary, lower memory, fast startup. The honest trade-off is that Go server-side Modbus libraries are noticeably less feature-rich than pymodbus, and you'd be writing more code to recreate the JSON-driven config + HTTP control surface pymodbus gives you for free. Pick this only if you have a hard requirement for a single binary with zero runtime dependencies.
•	C# / .NET with NModbus: Reasonable if your team already lives in .NET — common in industrial. .NET 8 self-contained AOT gives you a single executable. Doesn't gain anything over Python for development speed. Choose only if .NET is already the team's first language.
•	Rust with tokio-modbus: Overkill. You're not building a flight controller. The dev-time penalty vs. Python is real; the runtime benefit is invisible at this workload.
•	Java with j2mod: You have Java skills from the Ignition SDK side, but JVM startup, packaging friction, and Maven/Gradle ceremony give you Python's downsides without Python's iteration advantage. Skip.
The specific stack I'd commit to:
•	Python 3.11+ (asyncio performance improvements help)
•	pymodbus 3.x, specifically ModbusSimulatorServer — one instance per port, or a thin orchestrator spawning N of them in one process
•	JSON config per simulated device, generated from your existing Modbus map (a small CSV→JSON shim, ~30 lines)
•	NSSM-wrapped Windows Service (or systemd unit on Linux) so it survives reboots and runs without an interactive session
•	pymodbus's built-in HTTP endpoint for fault injection — you can almost certainly skip writing a custom Flask/FastAPI wrapper, since the built-in API already covers register manipulation, response simulation, and call monitoring
The pymodbus-native ModbusSimulatorServer is the part most people miss when they roll their own simulator from scratch. Use it. You'll write substantially less code than you would with any other library in any other language.

The library: j2mod or Modbus4j
j2mod (github.com/steveohara/j2mod) is the actively-maintained fork of jamod. Apache 2.0, supports TCP/RTU/ASCII slave (server) mode, function codes 1/2/3/4/5/6/15/16, register/coil data stores you can populate at runtime. It's a single jar, no native dependencies, and it's the de facto standard for Modbus in Java land.
For your case, the relevant API is roughly:
java
ModbusSlaveFactory.createTCPSlave(port, poolSize)
slave.addProcessImage(unitId, processImage)  // your register map
slave.open()
That's the whole thing. No protocol implementation work on your end. j2mod handles transaction IDs, framing, exception codes, all of it.
Where it lives in your module
Gateway-scope module, single hook class. The pattern matches the managed-tag-provider example in your project files almost exactly — just substitute "register a managed tag provider" with "spin up N j2mod slaves." Rough shape:
•	GatewayHook.startup() reads config (CSV path, port range, register map source) and starts the slaves on a background thread.
•	Each slave gets its own ModbusSlaveTCPListener bound to a unique port on 0.0.0.0 (or whatever IP you want).
•	A managed tag provider exposes per-simulator status tags (port, connected client count, last-request timestamp) so operators can see what's running from a Perspective view without leaving the Gateway.
•	GatewayHook.shutdown() closes all slaves cleanly.

The real concerns at 200 ports inside the JVM
These are tractable, but worth being upfront about:
Thread model. j2mod's TCP listener defaults to a thread-per-connection model with a configurable pool. With 200 listeners and one Ignition client per port, that's ~200 listener threads plus ~200 worker threads at peak, so call it 400 threads of overhead. The Gateway JVM already runs hundreds of threads — this is real but not catastrophic. Set the pool size on each slave to 1 or 2, since you have exactly one Ignition client per simulator.
Memory. Each slave is small (low single-digit MB including the process image). 200 × that is well under a GB. Bump the Gateway's wrapper.java.maxmemory in ignition.conf by 1 GB to give yourself headroom and call it done.
Port binding. Make sure the ports you pick don't collide with anything else on the box. Stay above 1024 to avoid root/admin issues. 5000-5200 is a safer range than 501-700 because some systems reserve low ports.
Stability blast radius. This is the one I want to flag honestly. If the simulator has a bug that throws an unhandled exception or leaks sockets, it's running in the same JVM as your production Gateway. j2mod is mature and this risk is low, but it's not zero. Mitigations: wrap every j2mod entry point in try/catch Throwable, log via LoggerEx at error level, never let an exception propagate out of a slave thread, and put a kill switch in your config so an operator can disable all simulators without restarting the Gateway. You already know to do this, but it's worth saying out loud since the failure mode is "Gateway crash" instead of "kill the Python process."
Module signing. You'll need a dev signing cert to install the .modl on the Gateway. If you don't already have one set up, the gradle module plugin in your project files supports skipModlSigning for unsigned modules during dev — fine for an internal box, just don't ship that to anyone else.

The big shift: 8.3 module lifecycle is start-once
Modules are no longer started or stopped while the Gateway is already running. Instead, they are set up and started as the Gateway is starting, and shut down as the Gateway is shutting down. Any module changes while the Gateway is running will wait until a Gateway restart to take effect. inductiveautomation
This matters because your simulators are exactly the kind of thing operators will want to start/stop/reconfigure mid-test. You don't want "tweak a CSV row" to require a Gateway restart. The implication: build all per-simulator runtime control inside the module's runtime state (a manager class with start/stop/reconfigure methods), not via module enable/disable. Modbus Multi-Port Simulator Module — Specifications & Requirements (v0.1, MVP)
1. Purpose
Build a Gateway-scope Ignition 8.3.3 module that, on Gateway startup, launches N Modbus TCP slave (server) listeners on a single host IP, each on a unique TCP port. Listeners stay running for the lifetime of the Gateway and shut down cleanly when the Gateway shuts down. No UI, no operator controls, no runtime configuration. The module exists so an Ignition Modbus client (running on the same Gateway or elsewhere) can connect to up to 200+ simulated Modbus servers without external processes or containers.
2. Scope
In scope (MVP)
•	Gateway-scope-only module (no Designer, no Client, no Vision).
•	Single hook class implementing AbstractGatewayModuleHook.
•	Hardcoded or static-config-file-driven list of (port, unit ID) entries.
•	One Modbus TCP slave per port, all bound to 0.0.0.0 (listening on all interfaces of the Gateway host).
•	Each slave responds to function codes 1, 2, 3, 4, 5, 6, 15, 16 with deterministic, static register/coil contents (e.g., all registers initialized to a value derived from port number, or all zeros).
•	Clean startup and shutdown integrated with module lifecycle.

The four pieces
1. TagSourceService — a single background thread that polls a configured set of source tag paths from the Gateway's TagManager on a fixed interval (start at 250 ms, tunable). On each tick it produces a Map<TagPath, QualifiedValue> snapshot. This is the only component that talks to the Ignition tag system, which keeps the rest of the module a pure Modbus library wrapper. Use context.getTagManager().readAsync(...) for the reads — async, batched, doesn't block.
2. RegisterFanout — the routing table. Maps each source tag to one or more (port, register-address, register-type, scaling) destinations. This is the piece that makes 1 RTAC look like 200 devices: a single source tag like [default]SEL/RTAC1/GenStatus/Gen1_kW can be written to register 0 of port 5020, register 0 of port 5021, register 100 of port 5022 — whatever pattern matches what the MQTT consumers expect. Held as an immutable Map rebuilt only when config changes.
3. SimulatorRegistry — manages the 200 j2mod ModbusTCPListener instances and their ProcessImage register banks. Exposes one method that matters: applySnapshot(Map<TagPath, QualifiedValue>). It walks the snapshot, looks up each tag in the fanout, writes the scaled value into every destination register's process image. j2mod's ProcessImage is thread-safe for register writes, so this can happen concurrently with client reads.
4. ModbusSimulatorGatewayHook — the standard 8.3 hook. setup() constructs the three components above. startup() loads the routing config, starts the j2mod listeners, starts the polling thread. shutdown() reverses it all. Same lifecycle pattern as the bare-bones spec.

Loaded at startup, period. No live reload in MVP — that's a phase-2 add. Module restart picks up changes, which is fine because you control the Gateway.

The constant-value version validates that the module runs. It doesn't validate that the MQTT consumers see what they expect. By plumbing real tag data through, the FAT becomes: "does the MQTT cluster correctly process live RTAC data fanned out across 200 endpoints?" — which is the actual test that matters, and which I suspect will be the moment somebody discovers an issue with the cluster setup that vindicates the position you've been holding for months.
The complexity delta over the bare-bones spec is small: one extra service class for tag polling, one extra config-loading step, one method on the registry. The §10 acceptance criteria from the previous spec barely change; criterion 4 just becomes "reading register 0 from port 5020 returns the current value of [default]SEL/RTAC1/Gen1_kW, scaled."
Two things worth being explicit about
Stale data behavior. When the source tag goes Bad quality (RTAC comm loss, etc.), the simulator needs a defined response. Cleanest options: hold last known value, or return a Modbus exception code (slave device failure, 0x04). I'd default to hold last value, also raise a status flag in a reserved register so the MQTT consumer can see staleness if it's smart enough to look — and then make this configurable later. Don't return exceptions by default, because it'll cascade alarms in consumers that aren't expecting them during the FAT.
Write-back semantics. The MQTT cluster might attempt writes to these simulated registers. The bare-bones spec said "writes succeed and persist" but if this is a republisher, that's misleading because the writes go nowhere — they don't propagate back to the real RTAC. For MVP, accept writes silently into the local process image (so the cluster sees what it wrote), but log them at INFO so you can see what's being attempted. Don't propagate them anywhere. Real write semantics is a separate, harder design discussion.

What this confirms about the architecture
The fan-out map is your contract with the cluster, not with SEL. SEL doesn't care how you slice up their consolidated RTAC register space — they're just exposing whatever's not in RTDS as one big flat Modbus map. The 200-endpoint partitioning is entirely a VoltaGrid-side decision based on how the cluster's Modbus clients are configured to address devices in production. So the routing config (which source register goes to which simulated port + register) needs to match what the cluster expects to find, not what SEL exposes. Those are two different documents and you'll need both.
Source-side simplification. Since SEL is exposing one big consolidated Modbus TCP server, you actually have two reasonable ways to source the data:
1.	Read through Ignition's Modbus driver and TagManager — what I described before. The Gateway already has the connection, the data lives in tags, you read tags, you republish.
2.	Read directly from the SEL RTAC via your own embedded Modbus client — j2mod has a client side too, and you'd just read raw register blocks on a polling cycle and copy them into the fan-out destinations.
Option 2 is actually cleaner for what you're doing. Reasons:
•	You're moving raw register values from one Modbus server to 200 Modbus servers. Routing through Ignition's tag system means data goes bytes → tag (typed, scaled, qualified) → bytes again. That round trip introduces type coercion, scaling decisions, and quality semantics that don't matter for a passthrough simulator. It also couples your module to whatever tag paths happen to be configured in the Gateway today, which is fragile.
•	Option 2 gives you a self-contained module: point it at the SEL RTAC's IP, give it a register map, and it works. It doesn't care whether someone renames a tag, deletes a UDT instance, or breaks a binding in the Gateway.
•	Polling discipline is also better. You define your own poll cycle (say 250ms read of register block 0–9999 from the RTAC, write into the appropriate process images). Your simulator's data freshness is decoupled from however the rest of the Gateway is scanning.
•	The Gateway also keeps its existing direct connection to the RTAC for the real HMI, totally unaffected. Two clients on the RTAC's Modbus server is fine — it's TCP, it doesn't care.
The only reason to prefer Option 1 is if you want the simulator to participate in scaling, EU conversion, or quality logic that already lives in the Gateway's tag layer. For an FAT loopback simulator I don't think you do.
I'd recommend Option 2 unless you tell me there's a reason the data needs to be tag-sourced.
Stale data behavior, revisited. With Option 2, when the SEL RTAC connection drops, you know it directly — the j2mod client throws or times out. Cleanest behavior: hold last values for, say, 30 seconds, then start returning Modbus exception 0x0B (gateway target device failed to respond) on the simulated ports. But for FAT day-1, just hold-last-value silently and add the exception logic later. Don't let "perfect failure semantics" hold up the build.

Modbus Multi-Port Simulator Module — Specifications & Requirements (v0.2, Republisher MVP)
0. Revision Note
Replaces v0.1 (bare-bones synthetic-data simulator). v0.2 changes the data source from constant-seeded values to live republishing of an upstream SEL RTAC's consolidated Modbus TCP server, while preserving the same Gateway-scope Ignition module structure, lifecycle, and packaging.
1. Purpose
Build a Gateway-scope Ignition 8.3.3 module that, on Gateway startup, opens a passthrough connection to an upstream SEL RTAC Modbus TCP server and re-serves that server's register contents through 200 independent Modbus TCP slave listeners on a single host IP at unique ports. The cluster's Modbus clients connect to each port as if it were an individual physical device. All 200 listeners serve identical data sourced from the same upstream RTAC. The module exists so the FAT can validate the cluster's per-device polling and downstream MQTT pipeline against a deterministic, live-but-controlled data source, without requiring containers, external processes, or IT involvement.
2. Scope
In scope (MVP)
•	Gateway-scope-only module. No Designer, no Client, no Vision.
•	Single embedded Modbus TCP client that polls a configurable upstream SEL RTAC.
•	200 embedded Modbus TCP slave listeners on configurable ports, single host bind interface.
•	Each listener serves the full consolidated register map (Coils, Discrete Inputs, Input Registers, Holding Registers) with addresses preserved verbatim from the SEL source.
•	Periodic background poll of upstream source; in-memory copy applied to all slave process images.
•	Hold-last-value behavior on upstream comm loss.
•	Static configuration via JSON file in the Gateway data directory.
•	Clean lifecycle integration with Gateway startup/shutdown.
•	Gateway log output for startup summary, upstream connection state changes, and shutdown.
Out of scope (deferred)
•	Operator UI, status panel, Perspective view, homepage panel.
•	Configuration through extension points or config records.
•	Scripting functions for runtime control.
•	Live config reload without Gateway restart.
•	Per-port asset-filtered register subsets (every port serves the full map in MVP).
•	Modbus exception responses for stale data (uses hold-last-value silent default).
•	Write-back to upstream RTAC. Writes from the cluster are accepted into local process images and logged, but never propagated.
•	Managed tag provider exposing simulator status as Ignition tags.
•	Multi-IP host binding (deferred until/unless the cluster requires per-device IPs).
•	Module signing for production distribution (dev-unsigned only for MVP).
3. Target Environment
•	Ignition platform: 8.3.3.
•	JVM: Java 17 (bundled with Ignition).
•	Host OS: agnostic. Verified deployment will be whichever OS the FAT Gateway runs on.
•	Network bind: single IP, 200 contiguous unique ports. Suggested base 5020 (range 5020–5219); avoids privileged ports and the standard Modbus port 502. Final base port confirmed in §11.
•	Upstream source: one SEL RTAC, reachable by IP:port from the Gateway, presenting the consolidated Modbus TCP server documented in full-modbus-map-cl.xlsx (4,617 signals).
•	Module library dependency: j2mod (Apache 2.0). Bundled via modlImplementation, single jar.
4. Functional Requirements
4.1 Module Lifecycle
•	FR-1. setup(GatewayContext) retains the Gateway context reference and reads the static configuration file (see §7). If the file is missing or malformed, log an ERROR and skip module activation; do not throw out of setup().
•	FR-2. startup(LicenseState) opens the upstream Modbus client connection, instantiates 200 slave listeners with their process images, starts the polling thread, and returns. Listener and client startup occur on a background thread so Gateway startup is not blocked.
•	FR-3. shutdown() stops the polling thread, closes all 200 slave listeners, and closes the upstream client connection. All sockets must be released before the method returns. Shutdown must complete even if individual close calls throw.
•	FR-4. Module lifecycle conforms to 8.3 semantics: started once at Gateway startup, stopped once at Gateway shutdown. No mid-run reconfiguration in MVP.
4.2 Upstream Source Polling
•	FR-5. A single background thread polls the upstream SEL RTAC Modbus TCP server on a configurable cycle. Default poll interval: 250 ms.
•	FR-6. Per cycle, the poller issues read requests covering the configured upstream register blocks (see §7.2 — typically a small number of contiguous block reads per Modbus type, sized to cover the address ranges in the source map). The poller does not iterate one register at a time.
•	FR-7. Poll results populate an in-memory snapshot buffer with four maps (one per Modbus type), keyed by raw register address.
•	FR-8. On successful poll completion, the snapshot buffer is atomically published to all 200 process images.
•	FR-9. On upstream read failure (timeout, connection refused, exception response), the poller logs at WARN level (rate-limited to one per minute per failure type), retains the last-known snapshot, and continues polling. The slave listeners continue serving the held values.
•	FR-10. On upstream connection loss, the client attempts reconnection on a backoff schedule (immediate, 1s, 5s, 30s, then every 30s) and resumes normal polling on success. Slaves continue serving last-known values throughout.
4.3 Slave Listener Behavior
•	FR-11. Each slave binds to <configured-host-ip>:<port> where ports are 200 contiguous values starting at the configured base port.
•	FR-12. Each slave's process image exposes:
•	Coils for any address present in the source map's Coil range (0–657 in current map).
•	Discrete Inputs for any address present in the source map's Discrete Input range (10001–11345 in current map).
•	Input Registers for any address present in the source map's Input Register range (2970–32969 in current map).
•	Holding Registers for any address present in the source map's Holding Register range (1907–41907 in current map).
•	Addresses are preserved verbatim from the source map. No address translation, no offset normalization.
•	FR-13. All 200 process images contain identical data. After each successful upstream poll, every process image is updated with the same snapshot.
•	FR-14. Each slave responds to function codes 0x01, 0x02, 0x03, 0x04, 0x05, 0x06, 0x10, and (recommended) 0x0F. The current map uses 0x02, 0x04, 0x05, 0x06, and 0x10; supporting all common FCs costs nothing and avoids surprises.
•	FR-15. Each slave's TCP listener is configured with a thread pool of 1–2 worker threads, since the cluster will have at most a small number of concurrent clients per port.
•	FR-16. Writes from the cluster (FC 0x05, 0x06, 0x0F, 0x10) are accepted into the local process image, persist for the slave's lifetime, are logged at INFO level (with port, address, value), and are not propagated upstream to the SEL RTAC.
4.4 Logging
•	FR-17. On startup, log INFO: total slaves attempted, slaves successfully started, base port, host bind IP, upstream RTAC IP:port.
•	FR-18. On upstream connection state change (connected, disconnected, reconnected), log INFO.
•	FR-19. On upstream poll failure, log WARN (rate-limited per FR-9).
•	FR-20. On Modbus write received from cluster, log INFO: port, function code, address, value(s).
•	FR-21. On shutdown, log INFO: number of slaves stopped, upstream connection closed.
•	FR-22. Per-slave bind events log at DEBUG only (avoid 200 INFO lines on startup).
•	FR-23. All logging through SLF4J / LoggerEx. No System.out.
5. Non-Functional Requirements
5.1 Stability
•	NFR-1. No exception thrown by any j2mod thread (slave or client) propagates out of the module. Every entry point wraps try/catch Throwable, logs, and isolates the failure.
•	NFR-2. Failure to bind any single port (e.g., port already in use) does not prevent other slaves from starting. Failed slaves are logged and skipped; the module continues operating with the remaining slaves.
•	NFR-3. Upstream connection failure does not impact slave availability. Slaves remain bound and respond with last-known values.
•	NFR-4. Gateway shutdown must complete even if individual slaves throw on close.
5.2 Performance
•	NFR-5. Default 250 ms upstream poll cycle must complete within the cycle time under nominal conditions (one upstream connection, ~5,700 registers covered by a handful of block reads). If a cycle exceeds its interval, the next cycle starts immediately without queueing.
•	NFR-6. Process image update latency from snapshot to all 200 images: under 50 ms typical.
•	NFR-7. End-to-end freshness from upstream change to cluster-readable on any port: under 500 ms typical.
5.3 Resource Footprint
•	NFR-8. With 200 idle slaves, one upstream client connection, and one cluster client per slave, total module heap usage stays under 500 MB.
•	NFR-9. Total threads contributed by the module: under 500 (200 listener accept threads + ~200 worker threads + 1 poller + a few utility threads).
•	NFR-10. Recommend raising wrapper.java.maxmemory in ignition.conf by 1 GB above current setting prior to deployment. This is a deployment note, not a module requirement.
5.4 Build & Packaging
•	NFR-11. Built with Gradle, structure modeled on the opc-ua-device example. Uses io.ia.sdk.modl plugin.
•	NFR-12. Single Gradle subproject (gateway only). No common, client, or designer.
•	NFR-13. skipModlSigning = true for MVP. Module installed on Gateway with module acceptance enabled.
•	NFR-14. j2mod declared as modlImplementation to ensure it is bundled in the .modl.
5.5 Compatibility
•	NFR-15. Targets Ignition 8.3.3 SDK only. No 8.1 backward compatibility.
•	NFR-16. Uses 8.3-current APIs only: AbstractGatewayModuleHook, LicenseState, current GatewayContext. No deprecated APIs.

Build a Gateway-scope Ignition 8.3.3 module that opens a passthrough connection to an upstream SEL RTAC Modbus TCP server and re-serves the data through approximately 208 independent Modbus TCP slave listeners, on a single host IP at unique ports. Each listener presents the manufacturer's native Modbus map for the specific physical device it represents, populated with values translated from the SEL source. The cluster's Modbus clients connect to each port as if they were addressing the real production devices. The module exists so the FAT can validate the cluster's per-device polling and downstream MQTT pipeline against a deterministic, live-but-controlled data source, with each endpoint behaving as production-realistically as possible.
2. Scope
In scope (MVP)
•	Gateway-scope-only module. No Designer, no Client, no Vision.
•	Single embedded Modbus TCP client that polls the upstream SEL RTAC.
•	~208 embedded Modbus TCP slave listeners on configurable contiguous ports, single host bind.
•	Per-port destination register layout determined by device type (DIANE/B&R, SEL 700G, SEL 751, SEL 787, ECS100, CCP, etc.).
•	Per-port translation table mapping native destination registers to SEL source registers, derived offline from manufacturer documentation and the SEL consolidated map.
•	Periodic background poll of upstream source; values translated and applied to each port's process image.
•	Hold-last-value behavior on upstream comm loss.
•	Static configuration via JSON file in the Gateway data directory.
•	Clean lifecycle integration with Gateway startup/shutdown.
•	Gateway log output for startup summary, upstream connection state changes, and shutdown.
Out of scope (deferred)
•	Operator UI, status panel, Perspective view, homepage panel.
•	Configuration through extension points or config records.
•	Scripting functions for runtime control.
•	Live config reload without Gateway restart.
•	Modbus exception responses for stale data (uses hold-last-value silent default).
•	Write-back to upstream RTAC. Writes from cluster are accepted into local process images and logged, never propagated.
•	Managed tag provider exposing simulator status as Ignition tags.
•	Multi-IP host binding (deferred until/unless cluster requires per-device IPs).
•	Synthesizing values for native registers that have no SEL source counterpart — these are left unpopulated (Modbus reads return zero/false from j2mod's sparse process image default).
•	Module signing for production distribution (dev-unsigned only for MVP).
3. Target Environment
•	Ignition platform: 8.3.3.
•	JVM: Java 17 (bundled with Ignition).
•	Host OS: agnostic.
•	Network bind: single IP, contiguous unique ports starting at base 5020 (avoiding privileged range and standard 502).
•	Upstream source: one SEL RTAC, presenting the consolidated Modbus TCP server documented in full-modbus-map-cl.xlsx (4,617 signals across 4 Modbus types, 203 unique Asset Names).
•	Dependency: j2mod (Apache 2.0) bundled as a single jar.
4. Functional Requirements
4.1 Module Lifecycle
•	FR-1. setup(GatewayContext) retains context, reads the static config, and instantiates module components. If config is missing or malformed, log ERROR and skip activation; do not throw.
•	FR-2. startup(LicenseState) opens the upstream connection, instantiates and binds all slave listeners with their per-port process images, and starts the polling thread. Listener binds and client connect occur on a background thread.
•	FR-3. shutdown() stops the polling thread, closes all listeners, and closes the upstream client. All sockets must be released before return. Shutdown completes even if individual closes throw.
4.2 Upstream Source Polling
•	FR-4. A single background thread polls the upstream SEL RTAC on a configurable cycle. Default 250 ms.
•	FR-5. Per cycle, the poller reads the configured upstream register blocks (sized to cover the address ranges of source registers actually referenced by at least one port — see §7 and the offline helper script in §12).
•	FR-6. Poll results populate a single in-memory SourceSnapshot keyed by SEL source address per Modbus type.
•	FR-7. On successful poll, the snapshot is published and each port's process image is updated via that port's translation table (§4.4).
•	FR-8. On read failure, log WARN (rate-limited, one per minute per failure type), retain last snapshot, continue polling.
•	FR-9. On connection loss, attempt reconnect with backoff (immediate, 1s, 5s, 30s, then 30s steady) and resume on success. Slaves continue serving last-known values throughout.
4.3 Slave Listener Behavior (per port)
•	FR-10. Each slave binds to <bindHost>:<port>. Ports are contiguous starting at the configured base port; port count and ordering are determined by the port assignment list in config.
•	FR-11. Each slave's process image is sized and populated according to its assigned device type's native Modbus map. Addresses, types (Coil / DI / IR / HR), and data widths are exactly as specified in that manufacturer's documentation.
•	FR-12. Process images are sparse: only addresses that exist in the device type's native map are populated. Reads of unmapped addresses behave per j2mod default (zero / false / illegal address response — j2mod's choice; consistent across all ports).
•	FR-13. Each slave responds to FCs 0x01, 0x02, 0x03, 0x04, 0x05, 0x06, 0x10, and 0x0F. Native maps that don't use a given FC simply have no addresses for it.
•	FR-14. Each slave's TCP listener uses a thread pool of 1–2 worker threads.
•	FR-15. Writes from the cluster are accepted into the local process image, persist for the slave's lifetime, are logged at INFO level (port, FC, address, value), and are not propagated upstream.
4.4 Translation Layer (the new component)
•	FR-16. Each port has a fully-resolved translation table: a list of (destAddr, destType, sourceAddr, sourceType, dataWidth) tuples. The table is built once at module startup from the configuration.
•	FR-17. On each successful upstream poll, the translation engine walks every port's table and copies values from the source snapshot into that port's process image at the destination addresses, using the appropriate Modbus type at each end.
•	FR-18. When source and destination Modbus types match (e.g., source IR → dest IR), values are copied verbatim including byte order and data width — no scaling, no endianness change. The simulator presents data byte-identical to what the upstream returned.
•	FR-19. When source and destination Modbus types differ (e.g., source Coil → dest Discrete Input, or source HR → dest IR), the value is copied with type coercion only (boolean → boolean for Coil/DI swaps; register-width values copied unchanged for IR/HR swaps). Address-and-type pairs are recorded explicitly in each port's translation table; no inference at runtime.
•	FR-20. If a destination address in a port's native map has no corresponding source entry in the translation table, that destination is simply not populated. The port's process image remains sparse at that address.
•	FR-21. Translation is purely a data-driven lookup. The runtime module contains no device-specific logic; all device knowledge lives in the configuration.
4.5 Logging
•	FR-22. On startup, log INFO: total slaves attempted, slaves successfully started, base port, host bind, upstream IP:port, count of distinct device types in config.
•	FR-23. On upstream connection state change, log INFO.
•	FR-24. On poll failure, log WARN (rate-limited per FR-8).
•	FR-25. On Modbus write received from cluster, log INFO with port, FC, address, value.
•	FR-26. On shutdown, log INFO: slaves stopped, upstream disconnected.
•	FR-27. Per-slave bind events at DEBUG only.
•	FR-28. All logging via SLF4J / LoggerEx.
5. Non-Functional Requirements
5.1 Stability
•	NFR-1. No j2mod thread exception propagates out of the module. Every entry point wraps try/catch Throwable.
•	NFR-2. Single-port bind failure does not stop other slaves.
•	NFR-3. Upstream connection failure does not impact slave availability.
•	NFR-4. Gateway shutdown completes even if individual slaves throw on close.
5.2 Performance
•	NFR-5. Default 250 ms poll cycle completes within the cycle time. With ~208 ports and total translation table size proportional to the union of all device types' register counts, end-to-end snapshot-to-all-images latency stays under 100 ms typical.
•	NFR-6. End-to-end freshness from upstream change to cluster-readable on any port: under 500 ms typical.
5.3 Resource Footprint
•	NFR-7. With ~208 idle slaves, one upstream connection, and one cluster client per slave, total module heap stays under 500 MB.
•	NFR-8. Total threads contributed by the module: under ~520 (208 listener accept threads + ~208 worker threads + 1 poller + utility threads).
•	NFR-9. Recommend raising wrapper.java.maxmemory in ignition.conf by 1 GB above current setting prior to deployment.
5.4 Build & Packaging
•	NFR-10. Built with Gradle, structure modeled on opc-ua-device example. Uses io.ia.sdk.modl plugin.
•	NFR-11. Single Gradle subproject (gateway only).
•	NFR-12. skipModlSigning = true for MVP.
•	NFR-13. j2mod declared as modlImplementation.
5.5 Compatibility
•	NFR-14. Targets Ignition 8.3.3 SDK only. No 8.1 backward compatibility.
•	NFR-15. Uses 8.3-current APIs only: AbstractGatewayModuleHook, LicenseState, current GatewayContext. No deprecated APIs.

Classes (6 total, one Gradle subproject)
ModbusSimulatorGatewayHook extends AbstractGatewayModuleHook — entry point. setup() loads config and instantiates components. startup() starts client, registry, poller. shutdown() reverses.
SimulatorConfig — immutable record loaded from JSON at startup. Holds upstream connection settings, host bind, base port, poll interval, list of PortAssignment records (port → assetName → deviceType → translation table).
ModbusSourceClient — wraps a j2mod ModbusTCPMaster. Owns the upstream connection, polling thread, reconnect/backoff. Per cycle, issues block reads, builds a SourceSnapshot, hands it to TranslationEngine.
SourceSnapshot — immutable: four maps (Map<Integer, Boolean> for coils and discrete inputs, Map<Integer, Integer> for input and holding registers, treating each register as a 16-bit unsigned). Plus timestamp and upstream-reachable flag. Replaced atomically each successful poll.
TranslationEngine — pure data-driven. On apply(snapshot, registry), iterates each port's pre-computed translation table and copies values into the corresponding ProcessImage. Single-pass, no per-register decision-making at runtime.
SimulatorRegistry — manages all slave listeners and process images. start() binds all listeners (skipping individual bind failures). getProcessImage(port) exposes the image for the translation engine to write into. stop() closes all listeners.

8. Acceptance Criteria
Module is complete when all of the following hold:
1.	The .modl builds via ./gradlew buildModule with no errors.
2.	The .modl installs on a clean Ignition 8.3.3 Gateway after module acceptance.
3.	Gateway startup log contains an INFO line of the form: Modbus Simulator: started N/N slaves on <bind>:<base>-<base+N-1>, upstream <host>:<port> connected, device types loaded: <list>.
4.	From a Modbus TCP client (pymodbus, OpenModSim client, etc.), connecting to the port assigned to GEN1 and reading the GEN1 active power register at the address specified in DIANE/B&R's native map returns the same value as reading the corresponding GEN1 active power register from the upstream SEL RTAC, within 500 ms of an upstream change.
5.	Connecting to the port assigned to GCB-01 (the GEN1 generator circuit breaker) and reading at addresses specified in SEL 700G's native map returns values that correspond to the SEL source signals associated with Asset Name GEN1 (or whatever the actual SEL Asset Name is for GEN1's GCB).
6.	The two ports above return different sets of registers at different addresses, reflecting their different native maps. Reads of addresses present in one device type's map but not the other return per-FR-12 default behavior on the port that doesn't use them.
7.	With the upstream RTAC disconnected, all ports continue responding with last-known values. Log shows WARN entries (rate-limited) and INFO on disconnect detection.
8.	With the upstream RTAC reconnected, polling resumes and slaves return live values within one poll cycle. INFO log entry confirms reconnection.
9.	A write from the cluster to a holding register on one port is accepted, persists when read back from that same port, does not appear on any other port, and does not appear on the upstream RTAC. INFO log records the write.
10.	With one configured port occupied at startup, that one bind failure is logged and the module continues with the remaining slaves; criteria 4–9 still pass for those.
11.	Module memory and thread usage remain stable over a 30-minute idle run. No memory growth.
12.	Gateway shutdown emits the INFO line Modbus Simulator: stopped N slaves, upstream disconnected. Subsequent restart shows no bind: address already in use errors.

Modbus Multi-Port Simulator Module — Specifications & Requirements (v0.4-MVP-walking-skeleton)
0. Revision Note
Replaces v0.3 for first-build purposes only. Strips out:
•	Upstream Modbus client and polling.
•	Translation engine.
•	JSON config file (replaced with a hardcoded constant).
•	Manufacturer native maps (replaced with synthetic obvious values).
•	Hold-last-value, reconnect logic, poll-cycle requirements.
•	Most acceptance criteria.
What remains is the load-bearing structure: a Gateway-scope module that binds N ports on a single IP and serves canned Modbus data on each. v0.3 is the production target; this is the proof-of-life that gets us there.
1. Purpose
Get a working .modl deployed on Ignition 8.3.3 that binds N Modbus TCP slaves on configurable contiguous ports of a single host IP, each serving a small distinct register set, so Miguel can connect a Modbus client (pymodbus, OpenModSim) port-by-port and verify the lifecycle, port binding, j2mod wiring, and Gateway integration all work end-to-end.
2. What it does
•	Starts on Gateway startup. Stops on Gateway shutdown.
•	Binds 5 slaves (configurable in code) on 0.0.0.0:5020 through 0.0.0.0:5024.
•	Each slave serves the same register layout, but with values that encode the port number so it's obvious which one you connected to:
•	Holding Register 0: the port number itself (e.g., port 5020 returns 5020).
•	Holding Register 1: a counter that increments once per second.
•	Holding Register 2: a fixed sentinel value 0xCAFE (so byte-order issues are visible).
•	Input Register 0: the slave index (0 through 4).
•	Coil 0: alternates true/false every second.
•	Discrete Input 0: always true.
•	A single background "ticker" thread updates the counter and the alternating coil on all slaves once per second.
•	Logs INFO on startup with the bind summary, and INFO on shutdown.
That's the whole feature set.
3. Target Environment
•	Ignition 8.3.3, Java 17.
•	Bind on 0.0.0.0 (all interfaces) for MVP — easier to test from the same host or another machine without coordinating IPs. v0.3 will switch to a configured single IP.
•	Ports 5020–5024.
•	Dependency: j2mod bundled as modlImplementation.
4. Functional Requirements
•	FR-1. setup() does nothing meaningful (logs DEBUG that it ran).
•	FR-2. startup() binds 5 j2mod ModbusSlaveTCP instances on ports 5020–5024 sequentially. For each slave: create a ProcessImage for unit ID 1, populate the registers per §2, register it on the slave, call slave.open(). After all 5 are open, start the ticker thread. Log INFO: Modbus Simulator MVP: N/5 slaves up on 0.0.0.0:5020-5024.
•	FR-3. Per-slave bind failure does not abort the rest. Failed binds log WARN with the port; remaining slaves still come up. INFO summary reflects the actual count.
•	FR-4. The ticker thread runs once per second:
•	Increments HR1 on every slave (16-bit unsigned, wraps at 65535).
•	Toggles Coil 0 on every slave.
•	All other registers stay constant.
•	FR-5. Ticker thread uses a ScheduledExecutorService and stops cleanly when shutdown() is called. Any exception in the tick is caught and logged at WARN; ticker keeps running.
•	FR-6. shutdown() stops the ticker, calls close() on every slave, releases all sockets, returns. No exceptions propagate.
•	FR-7. Writes from clients to any register are accepted into the local process image (j2mod default). Logging of writes is not required for MVP.
5. Non-Functional Requirements
•	NFR-1. try/catch Throwable around the ticker body so the thread never dies.
•	NFR-2. Build output is a single unsigned .modl (skipModlSigning = true).
•	NFR-3. Total source: 2 Java classes, ~150 lines of Java, plus Gradle build files. Zero JSON, zero external config.
•	NFR-4. Module installs on a clean 8.3.3 Gateway via the Gateway's module-install UI with module-acceptance enabled.

Classes (2 total)
ModbusSimulatorGatewayHook — extends AbstractGatewayModuleHook. Owns the list of SlaveBundle instances and the ScheduledExecutorService. Lifecycle methods only.
SlaveBundle — encapsulates one j2mod ModbusSlaveTCP plus its ProcessImage. Constructor takes the port and slave index, builds the canned register set per §2, and prepares the slave (does not open it yet). open() calls slave.open(). tick() increments HR1 and toggles Coil 0. close() closes the slave.

8. Acceptance Criteria
Module is "done" for this phase when:
1.	./gradlew buildModule produces an unsigned .modl with no errors.
2.	The .modl installs on a clean Ignition 8.3.3 Gateway.
3.	After Gateway startup, the wrapper log contains: Modbus Simulator MVP: 5/5 slaves up on 0.0.0.0:5020-5024.
4.	From any Modbus TCP client (pymodbus one-liner is fine), connecting to <gateway-ip>:5020 and reading Holding Register 0 returns 5020. Reading HR0 from port 5021 returns 5021. Same pattern for 5022, 5023, 5024.
5.	Reading HR2 returns 0xCAFE (51966 decimal) on every port. (Confirms register width / byte order is sane.)
6.	Reading HR1 twice with a 2-second gap shows the value increased by ~2.
7.	Reading Coil 0 twice with a 2-second gap shows it toggled.
8.	Reading Input Register 0 returns the slave index: 0 on port 5020, 1 on port 5021, … 4 on port 5024.
9.	Gateway shutdown emits Modbus Simulator MVP: stopped 5 slaves. Subsequent Gateway restart shows no "address already in use" errors on ports 5020–5024.

11. Verification recipe (for the README)
A pymodbus one-liner you can run from the same host or any machine on the network:
bash
python3 -c "
from pymodbus.client import ModbusTcpClient
for port in range(5020, 5025):
    c = ModbusTcpClient('GATEWAY_IP', port=port)
    c.connect()
    hr = c.read_holding_registers(0, count=3, slave=1).registers
    ir = c.read_input_registers(0, count=1, slave=1).registers
    coil = c.read_coils(0, count=1, slave=1).bits[0]
    print(f'port {port}: HR={hr} IR={ir} Coil0={coil}')
    c.close()
"
Expected output should clearly show each port returning its own port number in HR0, sequential indices in IR0, and the same 0xCAFE sentinel everywhere.
